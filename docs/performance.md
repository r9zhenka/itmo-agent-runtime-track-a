# Infrastructure measurement and complete acceptance

The infrastructure measurements and prepared-host acceptance commands do not call
a live LLM. Historical measurement artifacts remain tied to their recorded source
revision; later lifecycle fixes have not silently replaced those samples. See the
[fixes and current validation report](cp2-fixes.md).

Measurements preserve raw samples and report median,
minimum, maximum and nearest-rank p95 (`sorted[ceil(0.95*n)-1]`). Use at least ten
repeats; at n=10, nearest-rank p95 is the maximum sample. Reports include OS/kernel,
architecture and Python metadata. Report actual host/VM resources and conditions
with the evidence; do not compare different machines as if only software changed.

## Mounted filesystem

Run on the client with the same source revision on the server, an active Compose
stack, SSH key authentication, and the server's `CLIENT_TOKEN` in the environment:

```bash
python3 -m scripts.measure_mount \
  --ssh-host project-a-ubuntu \
  --server-repo /home/bebra/itmo-agent-runtime-track-a \
  --ssh-config /home/r9zhenka/.ssh/config \
  --repeats 10
```

Use your own SSH alias and paths. The script creates a disposable client fixture:
32 small files (4 KiB each) in four directories, a 4 MiB large file and a 1 MiB
write target. It first measures a local baseline, then exports the same directory
using the production RemoteClient/WebDAV/SSH/rclone FUSE path. A trusted worker on
the server verifies the active mount and lease before measuring the filesystem
calls. No measurement code is generated by a model.

Each repeat measures:

- One `stat` of a 4 KiB file.
- Full recursive traversal of the fixture tree.
- Reading all 32 small files as one batch (not per-file latency).
- Reading the 4 MiB file completely.
- Replacing and closing the 1 MiB output file.

The worker checks bytes and paths outside the timing intervals. The client also
verifies the last write locally. Timing occurs inside the worker, excluding SSH
startup, gateway/session creation and Docker startup. It measures server-host
filesystem calls through the real mount, not container scheduling latency.

Reports are in `results/mount-performance.json`, with `local_baseline` and
`mounted` raw rows and summaries. The local baseline runs on the client and remote
calls on the server; hardware/VM scheduling differences remain confounders. Reads
use the production uncached rclone VFS configuration, but OS page caches are not
dropped: these are repeated/warm-cache measurements, not cold-disk bandwidth.
Write timing includes close/PUT acknowledgement; it is not a cross-machine
power-loss durability guarantee. The client directory is removed only after the
remote session has been released and the exporter closed.

## Docker sandbox

Run on the Docker host as the normal non-root Docker user after building the
sandbox image:

```bash
python3 -m scripts.measure_sandbox --repeats 10
```

The script uses real Docker containers with the project's production resource,
network and privilege configuration, in a disposable local fixture. Local RW is
explicitly enabled for that trusted measurement only.

`results/sandbox-performance.json` contains:

- `cold_start_ms`: create/start until an idle Python process emits its ready log,
  measured with a 5 ms polling interval. The image is already cached; image pulls
  and cache eviction are excluded. It is a fresh-container start, not a cold image.
- `exec_lifecycle_ms`: complete `SandboxManager.exec` for `python -c 'pass'`,
  including container creation, execution, polling, logs and removal. This runtime
  uses a new container per operation; it has no persistent-container exec latency.
- `host_python_ms` and signed `exec_overhead_ms`: equivalent fresh Python process
  directly on the same Docker host, and the difference in elapsed time.
- Current Docker cgroup memory usage for an idle Python container and an idle
  `sleep` container with the same configuration, plus their signed difference.
  Charged file cache is included and also reported separately. This is measured
  container memory, not total dockerd/containerd/shim/host memory overhead or a
  peak-memory claim. Readings are taken after the ready marker.

All containers are removed in `finally` blocks. Any failed command or missing
memory sample fails the run; partial raw records are retained with `passed=false`.

## One-command complete offline checks

Preparation can use the internet. On Ubuntu, install Docker/Compose, Python 3.12+,
OpenSSH client/server and FUSE, enable `user_allow_other` in `/etc/fuse.conf`, then:

```bash
python3 -m scripts.init
python3 -m scripts.install_rclone
docker compose build
```

After preparation, the complete acceptance suite runs without external-network
requests or live model calls:

```bash
# CI host with passwordless sudo: creates a temporary loopback sshd.
make check-all

# Development Ubuntu VM with a running sshd: no sudo is needed by the suite.
make check-all CHECK_ARGS=--existing-sshd
```

The existing-sshd mode adds a temporary key restricted to localhost to the current
user's `authorized_keys`, verifies the local server against `/etc/ssh` public host
keys, and removes only its own key in `finally`. The normal CI mode starts a
separate ephemeral sshd with temporary keys instead. A SIGKILL/power loss can
interrupt cleanup; temporary key comments start `project-a-check-`.

The suite copies source/templates only into a temporary checkout and starts a
separate Compose project on a free loopback port. It never copies the original
`.env`, user workspaces, Git metadata or live model credentials. Model settings
are explicitly cleared and replay mode is checked against the running service.
Images must already exist: startup uses `--no-build --pull never`.

It runs offline unit/CLI/HTTP tests, actual Docker isolation, the separate code
grader, adversarial hardening tests, every registered BAF once using synthetic
replay, real rclone WebDAV and SSH/FUSE/Docker acceptance, helper-SIGKILL cleanup,
and actual controller-crash checks in the disposable stack. The BAF result file
must contain each registered task exactly once with synthetic provenance and
passing verdicts. The manager-crash check requires a removal event from the actual
surviving watchdog, not a manual invocation of its reaper.

The suite also audits all nine bundled actual-provider smoke recordings, recreates
only its own proxy in `LLM_MODE=recorded`, and runs the nine tasks through the real
runtime. It requires `recorded-replay` provenance, zero live provider calls and
no quality claim. Changed fixture, prompt, tools or substantive tool output causes
playback to fail rather than silently accepting a different conversation. The
[fixes report](cp2-fixes.md) tracks completion of the new recordings and acceptance.
The temporary Compose stack is torn down with its volumes; the user's live stack
is not restarted. Logs, raw reports and `summary.json` go to `results/check-all/`.

`make test-ci` remains the fast stdlib-only offline suite. The GitHub workflow runs
it separately and runs `make check-all` after preparing the Docker/FUSE toolchain.
The checks do not download tools or images; loopback, SSH and Docker bridge traffic
are still needed. A successful loopback CI mount test is not a two-machine demo.

## Summarize a model campaign

Keep each campaign's raw JSONL file separate from replay and from reruns. After a
full or partial run, generate a machine-readable summary and a Markdown matrix:

```bash
python3 -m scripts.summarize_benchmark \
  --input results/live-campaign.jsonl --repeats 3 \
  --output results/live-summary.json --markdown results/live-summary.md
```

By default, completeness is checked against every currently registered task
(39 tasks × 3 repeats = 117 attempts per pair). Multiple input files can be passed
after `--input` to compare distinct pairs. `--expected-task B1.1` can narrow the
expectation for a deliberate smoke campaign; repeat the option for multiple tasks.
`--pair LABEL` can include a planned pair with no completed attempts yet.

The summary contains every expected task, success/failure/missing counts, BAF × pair
rates, per-repeat rates and their population standard deviation/range, reported
tokens, median/p95 duration and generation time, and every failed attempt's reason.
Missing attempts remain visible and do not become observed failures; an additional
expected-denominator lower-bound rate shows coverage effects. Spread is calculated
only across complete repeats and states its sample count.

Duplicate `(pair, task, repeat)` entries are rejected instead of selecting the best
or latest result. One pair cannot change model ID mid-campaign. Mixed live/replay
files, contradictory provenance markers and malformed JSONL are rejected. Replay
and entirely unverified failures never establish model-quality evidence. Failed
attempts without model metadata are retained alongside verified live attempts,
count against observed success, and mark their token usage unknown. Reported token
totals are lower bounds when provider failures or missing metadata leave usage
unreported; they are not billing totals. Timings include failed attempts when the
runner recorded them. Environment/model eligibility and equivalence between pairs
still need to be documented separately from this aggregate.
